## インシデント:管理アカウントに IAM ユーザーを作ってしまった(2026-11-20)
| 項目 | 内容 |
|---|---|
| 起きたこと | SCP の試験で、dev アカウントで実行するはずの `aws iam create-user` が、**管理アカウント** で実行され、IAM ユーザーが1つ作られた |
| 影響 | なし。作られたユーザーにはアクセスキー・パスワード・権限がなく、使えない状態だった。数分以内に削除し、管理アカウントの IAM ユーザーが0に戻ったことを確認した |
| 原因 | zsh で `$DEV:role` と書いたため、`:r` が「拡張子を取る」修飾子として解釈され、ロールの ARN が壊れた。AssumeRole が失敗したが、コマンドを `;` でつないでいたため、元の認証情報(管理アカウント)のまま後続のコマンドが動いた |
| 気づいたきっかけ | 試験の出力に、拒否のメッセージではなく作成成功(`"UserName"`)が出たこと |
| 対応 | ユーザーにキー・パスワード・権限がないことを確かめてから削除した |
| 再発防止 | ① 変数は `${DEV}` のように波かっこで囲む。② 試験はスクリプトにし、`set -euo pipefail` で失敗したら止める。③ 書き込みを伴う試験の前に、`get-caller-identity` で **対象のアカウントにいることを確かめ、違えば中止する** |
| 学んだこと | SCP は管理アカウントには効かない。だからこそ管理アカウントで作業しない(DOC-03 4.2)という方針が大事で、今回はその弱点が実際に表に出た。CloudTrail の操作記録(P1-3)があれば、こうした操作も後から追える |

## インシデント:公開の CI ログにメンバーアカウントのIDが出た(2026-11-20)
| 項目 | 内容 |
|---|---|
| 起きたこと | PR #3 の最初の CI(plan の terraform/org)のログに、新しい4つのアカウントのIDが出た。メールアドレスは出ていない |
| 原因 | `configure-aws-credentials` が隠すのは、ロールのあるアカウント(管理アカウント)のIDだけ。org の plan では、各アカウントのIDが「Refreshing state... [id=...]」として出力される |
| 対応 | CI に「組織の全アカウントのIDを `::add-mask::` で隠す」手順を追加した。次の実行から、IDが `***` になることを確認した |
| 古いログの扱い | **削除せずに残す(リスクを受け入れる)。** 理由:① AWS はアカウントIDを秘密情報として扱っておらず、IDだけでは操作できない(認証情報と、SCP・最小権限の IAM で守っている)。② このリポジトリはポートフォリオで、問題に気づいて直した経緯の記録としても価値がある |
| 学んだこと | 「秘密の値を Secret に置く」だけでは足りず、ツールが自分で出力する値(リソースのID)も、ログを公開する前提で隠す必要がある。新しいスタックを CI に足すときは、最初の実行のログを必ず確かめる |

## つまずいたこと:P1-3b の detection の適用(2026-11-20)
| # | エラー | 原因 | 対応 |
|---|---|---|---|
| 1 | GuardDuty の検知器を作れない(既にある) | security を委任管理者にすると、AWS が自動で検知器を作る | 既存の検知器を import |
| 2 | security で Security Hub を有効にできない(既に有効) | 同じく、委任管理者にすると自動で有効になる(CIS の基準も自動で入った) | import。CIS は一元設定のポリシー(FSBP だけ)で外れた |
| 3 | Access Analyzer の組織の分析器を作れない | 管理アカウントに Access Analyzer のサービスリンクロールが必要 | 管理アカウントにロールを作成。作成直後は反映が間に合わず失敗したが、再実行で成功 |
| 4 | Config の配信チャネルを作れない(InsufficientDeliveryPolicyException) | ① バケットポリシーの条件 `aws:SourceOrgID` を `AWS:SourceAccount` に変えても失敗。② オブジェクトロックの既定の保持期間があるバケットへのアップロードには Content-MD5 などのチェックサムが必須で、Config の書き込みがそれを満たさないと判断 | Config 用に、オブジェクトロックなしの別のバケット(`zero-trust-minato-logs-config-*`)を作った。名前を `logs-` で始めて SCP の protect-logs で守り、バージョニングで戻せるようにした。新しいバケットでは Config の書き込みが成功し、原因の判断が正しかったことを確かめた |

### 学んだこと
- 委任管理者にすると、サービスによっては AWS が自動でリソースを作る。Terraform で「作る」のではなく「取り込む」ことを前提に設計する
- オブジェクトロックは強いが、書き込む側(サービス)にも条件がつく。「改ざんさせたくない証拠」(CloudTrail)と「設定の履歴」(Config)で、守り方を分けた
- エラーメッセージ(Insufficient delivery policy)が本当の原因(チェックサムの必須化)を指していないことがある。仮説を立て、切り分けて確かめる

## つまずいたこと:P1-4 の AR-3(2026-11-20)
| 項目 | 内容 |
|---|---|
| 起きたこと | 通知は送られたが、検知結果のワークフローの状態が NEW のままだった。Lambda はエラーなく終わっていた |
| 原因 | `batch_update_findings` は失敗しても例外を出さず、`UnprocessedFindings` に入れて返す。取り込みの直後(0.5秒以内)に呼んだため、検知結果がまだ見つからなかったと判断(手で呼ぶと成功した) |
| 対応 | 失敗を `UnprocessedFindings` で確かめてログに出し、0・2・5・10秒の間隔でやり直すようにした |
| 学んだこと | 「エラーが出ない = 成功」ではない API がある。戻り値を確かめ、失敗をログに残す。試験では「通知が届いたか」だけでなく「状態が変わったか」まで確かめる |
