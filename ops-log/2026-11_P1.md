## インシデント:管理アカウントに IAM ユーザーを作ってしまった(2026-11-20)
| 項目 | 内容 |
|---|---|
| 起きたこと | SCP の試験で、dev アカウントで実行するはずの `aws iam create-user` が、**管理アカウント** で実行され、IAM ユーザーが1つ作られた |
| 影響 | なし。作られたユーザーにはアクセスキー・パスワード・権限がなく、使えない状態だった。数分以内に削除し、管理アカウントの IAM ユーザーが0に戻ったことを確認した |
| 原因 | zsh で `$DEV:role` と書いたため、`:r` が「拡張子を取る」修飾子として解釈され、ロールの ARN が壊れた。AssumeRole が失敗したが、コマンドを `;` でつないでいたため、元の認証情報(管理アカウント)のまま後続のコマンドが動いた |
| 気づいたきっかけ | 試験の出力に、拒否のメッセージではなく作成成功(`"UserName"`)が出たこと |
| 対応 | ユーザーにキー・パスワード・権限がないことを確かめてから削除した |
| 再発防止 | ① 変数は `${DEV}` のように波かっこで囲む。② 試験はスクリプトにし、`set -euo pipefail` で失敗したら止める。③ 書き込みを伴う試験の前に、`get-caller-identity` で **対象のアカウントにいることを確かめ、違えば中止する** |
| 学んだこと | SCP は管理アカウントには効かない。だからこそ管理アカウントで作業しない(DOC-03 4.2)という方針が大事で、今回はその弱点が実際に表に出た。CloudTrail の操作記録(P1-3)があれば、こうした操作も後から追える |

## インシデント:公開の CI ログにメンバーアカウントのIDが出た(2026-11-20)
| 項目 | 内容 |
|---|---|
| 起きたこと | PR #3 の最初の CI(plan の terraform/org)のログに、新しい4つのアカウントのIDが出た。メールアドレスは出ていない |
| 原因 | `configure-aws-credentials` が隠すのは、ロールのあるアカウント(管理アカウント)のIDだけ。org の plan では、各アカウントのIDが「Refreshing state... [id=...]」として出力される |
| 対応 | CI に「組織の全アカウントのIDを `::add-mask::` で隠す」手順を追加した。次の実行から、IDが `***` になることを確認した |
| 古いログの扱い | **削除せずに残す(リスクを受け入れる)。** 理由:① AWS はアカウントIDを秘密情報として扱っておらず、IDだけでは操作できない(認証情報と、SCP・最小権限の IAM で守っている)。② このリポジトリはポートフォリオで、問題に気づいて直した経緯の記録としても価値がある |
| 学んだこと | 「秘密の値を Secret に置く」だけでは足りず、ツールが自分で出力する値(リソースのID)も、ログを公開する前提で隠す必要がある。新しいスタックを CI に足すときは、最初の実行のログを必ず確かめる |
