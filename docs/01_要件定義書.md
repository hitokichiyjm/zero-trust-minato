## 1. 背景と目的

### 1.1 背景
株式会社ミナト企画(架空)は、社員10名のWeb制作・マーケティング支援会社です。2024年からリモートワークを始めましたが、セキュリティは「社内ネットワークの中は安全」という考え方のままです。

- 社内アプリへは、共有アカウントのVPNで接続している
- AWSは1つのアカウントに本番と検証が混在しており、IAMユーザーのアクセスキーを複数人で使い回している
- ログは各サービスに散らばっていて、誰も定期的に見ていない
- 取引先から「セキュリティ対策の状況を説明してほしい」と求められたが、説明できる資料がない

### 1.2 目的
「ネットワークの場所ではなく、**人・端末・通信のたびに確認する**」ゼロトラストの考え方で、次を実現します。

1. **誰が・何に・どこからアクセスしたか** を、一人ひとりのIDで管理・記録する
2. VPNをやめ、**必要な人に必要なアプリだけ** を見せる
3. 脅威や設定ミスを **自動で検知し、自動で対応・通知** する(人の注意力に頼らない)
4. リスク・脅威・対応状況を **ダッシュボードで数字として示し**、経営者や取引先に説明できるようにする
5. 少人数でも回せるよう、**構成はコード化(Terraform)し、費用は低く抑える**

### 1.3 成功の基準(KGI)
| # | 基準 | 目標値(仮) |
|---|---|---|
| K-1 | 共有アカウント・長期アクセスキーの数 | 0 |
| K-2 | MFAを設定した社員の割合 | 100% |
| K-3 | 社内アプリにVPNなしで、許可した人だけが接続できる | 達成 |
| K-4 | 重大度High以上の検知から通知までの時間 | 15分以内 |
| K-5 | 期限を過ぎて放置されたアラートの件数 | 0件(自動でエスカレーションされる) |
| K-6 | 月額費用(常時かかる分) | 3,000円以内(上限5,000円でアラート) |

## 2. 対象範囲

### 2.1 対象とするもの
| # | 領域 | 概要 | 優先度 |
|---|---|---|---|
| S-1 | ID基盤 | SSO+MFA、権限の一元管理 | Must |
| S-2 | アクセス制御(ZTNA) | VPNなしの社内アプリ接続 | Must |
| S-3 | 検知 | AWSマルチアカウントでの脅威・設定ミスの検知 | Must |
| S-4 | 自動対応 | 検知をきっかけにした自動対応と通知 | Must |
| S-5 | ログ集約 | 各サービスのログを1か所に集めて検索する | Must |
| S-6 | ダッシュボード | リスク・脅威・対応状況の可視化とエスカレーション | Must |
| S-7 | CSPM | OSS「RISKEN」による設定の継続的な評価 | Could |
| S-8 | ハイブリッド接続 | 自宅VMをオンプレ拠点に見立て、Site-to-Site VPNで接続 | Could |

### 2.2 対象外とするもの
- 端末管理(MDM/EDR製品の導入)。ただし、端末の状態をアクセス条件に使う方法は方式設計で検討する
- メールセキュリティ(SPF/DKIM/DMARC 以外のゲートウェイ製品)
- 社内アプリそのものの機能開発(動作確認用の簡単なWebアプリだけを置く)
- 24時間365日の有人監視(SOC)

## 3. 会社の想定

### 3.1 組織と利用者
| 役割 | 人数 | 主な業務 | 必要なアクセス |
|---|---|---|---|
| 代表(経営者) | 1 | 経営判断、取引先対応 | 全アプリ閲覧、ダッシュボード、エスカレーションの受け手 |
| 情報システム担当(兼務) | 1 | IT・セキュリティ運用 | AWS管理者、全ログ、ダッシュボード |
| 開発 | 2 | 社内アプリ・顧客サイトの開発 | AWS検証環境の開発者権限、社内アプリ |
| 営業 | 3 | 顧客対応 | 社内アプリ(顧客管理) |
| 経理・総務 | 2 | 経理、労務 | 社内アプリ(経理機能)、社内Wiki |
| 外部委託(業務委託) | 1 | 開発の一部 | 検証環境の社内アプリだけ、期間限定 |

- 情報システム担当は兼務のため、**運用にかけられる時間は週2時間程度** とする(→ 自動化を重視する理由)
- 外部委託者がいるため、「社員と同じネットワークに入れない」アクセス制御が必要になる

### 3.2 利用環境
- 働く場所:自宅、出社(小さなオフィス)、外出先のWi-Fi
- 端末:会社支給のノートPC(Windows/Mac)、私物スマートフォン(メール・チャットのみ許可)
- 利用するSaaS:メール・カレンダー、チャット(通知先として使う)

### 3.3 システムと情報資産
| 資産 | 置き場所 | 重要度 | 理由 |
|---|---|---|---|
| 社内アプリ(顧客管理・経理) | AWS 本番アカウント(プライベートサブネット) | 高 | 顧客の個人情報、請求情報を扱う |
| 社内Wiki | AWS 本番アカウント | 中 | 手順書・社内情報 |
| 検証環境 | AWS 検証アカウント | 低〜中 | 開発用。本番データは置かない |
| ログ | AWS ログ用アカウント | 高 | 事故の調査に使う。改ざんされてはいけない |
| Terraformのコード・状態ファイル | GitHub、S3 | 高 | 構成の情報、秘密情報を含む可能性がある |

## 4. 現状の課題と目指す姿

| # | 現状(As-Is) | 問題 | 目指す姿(To-Be) | 対応する要件 |
|---|---|---|---|---|
| G-1 | VPNの共有アカウント | 誰が接続したか分からない。退職者も使える | 一人ひとりのIDでSSO、退職時は1か所で停止 | FR-ID |
| G-2 | VPNに入ると社内全体に届く | 1台の感染が全体に広がる | アプリ単位で許可(最小権限) | FR-AC |
| G-3 | IAMユーザーのアクセスキーを使い回し | キーが漏れると長期間悪用される | 一時的な認証情報だけを使う | FR-ID, NFR-SEC |
| G-4 | AWSアカウントが1つ | 検証の操作ミスが本番に影響する | 用途ごとにアカウントを分ける | FR-DT |
| G-5 | ログは散らばり、誰も見ていない | 攻撃に気づけない | 検知を自動化し、ログを集約 | FR-DT, FR-LG |
| G-6 | 対応は担当者の記憶頼み | 見落とし・放置が起きる | 自動対応+期限を過ぎたら自動エスカレーション | FR-RS, FR-DB |
| G-7 | 対策の状況を説明できない | 取引先の信頼を失う | 3観点のダッシュボードで数字で示す | FR-DB |

## 5. ゼロトラストの基本方針
NIST SP 800-207 の考え方をもとに、この会社での方針を次のように決めます。

| # | 方針 | この会社での具体化 |
|---|---|---|
| P-1 | 場所で信頼しない | 社内ネットワークからでも、外からと同じ確認をする |
| P-2 | アクセスのたびに確認する | アプリにアクセスするたびに、IDと条件(MFA、端末など)を確認する |
| P-3 | 最小権限 | 役割ごとに、必要なアプリ・権限だけを渡す |
| P-4 | 侵害されている前提で考える | 検知・自動対応・ログを用意し、被害を小さく抑える |
| P-5 | すべてを記録し、改善に使う | ログを集め、ダッシュボードで状況を見て対策を見直す |

## 6. 業務要件(利用シナリオ)

| # | シナリオ | 期待する動き |
|---|---|---|
| UC-1 | 営業が自宅から顧客管理アプリを使う | SSO+MFAでログインし、VPNなしでアプリが開く |
| UC-2 | 外部委託者が検証環境のアプリを使う | 許可した検証アプリだけが開き、本番アプリは見えない。契約終了日に自動で使えなくなる |
| UC-3 | 開発者がAWS検証アカウントを操作する | SSOでログインし、検証アカウントの開発者権限だけが使える。本番は閲覧のみ |
| UC-4 | 社員が退職する | IdPでアカウントを止めると、すべてのアプリとAWSに入れなくなる |
| UC-5 | AWSで不審な通信が検知される | 数分以内にチャットへ通知され、決めておいた対応は自動で行われる |

| UC-7 | アラートが期限までに対応されない | 代表に自動でエスカレーションされる |
| UC-8 | 代表が取引先に対策状況を説明する | ダッシュボードで「リスク・脅威・対応状況」を見せる |
| UC-9 | 情報システム担当が月に1回、状況を確認する | ダッシュボードと月次の数字で、改善点を決める |

## 7. 機能要件

優先度は MoSCoW(Must/Should/Could)で書きます。フェーズは「P1 = 応募時点(12月上旬)までの最小構成」「P2 = そのあと追加」です。

### 7.1 ID基盤(FR-ID)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-ID-01 | 社員・外部委託者は、一人ひとりのIDでSSOできること | Must | P1 |
| FR-ID-02 | すべての利用者にMFAを必須にすること | Must | P1 |
| FR-ID-03 | 役割(グループ)ごとに、AWSアカウントとアプリの権限を割り当てられること | Must | P1 |
| FR-ID-04 | AWSの操作は一時的な認証情報で行い、IAMユーザーの長期アクセスキーを作らないこと | Must | P1 |
| FR-ID-05 | ルートユーザーはMFAを設定し、普段は使わないこと | Must | P1 |
| FR-ID-06 | 外部委託者のアカウントに有効期限を設定できること | Should | P2 |
| FR-ID-07 | IdPでアカウントを止めると、つながるすべてのサービスに入れなくなること | Must | P2 |
| FR-ID-08 | 本番環境の管理者権限は、必要なときだけ使う運用(緊急用アカウントの手順を含む)にすること | Should | P2 |
| FR-ID-09 | 管理者はフィッシング耐性のあるMFA(パスキー/FIDO2)を使うこと。ほかの社員にも推奨すること | Should | P1 |

### 7.2 アクセス制御・ZTNA(FR-AC)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-AC-01 | 社内アプリへはVPNなしで接続できること | Must | P2 |
| FR-AC-02 | 社内アプリは、インターネットから直接届かない場所(プライベートサブネット)に置くこと | Must | P2 |
| FR-AC-03 | アプリごとに、接続してよいグループを決められること | Must | P2 |
| FR-AC-04 | 接続のたびに、IdPでの認証とMFAを確認すること | Must | P2 |
| FR-AC-05 | 許可・拒否したアクセスの記録が残ること | Must | P2 |
| FR-AC-06 | 端末の状態(OSの種類、会社支給かどうかなど)を接続の条件にできること | Could | P2 |
| FR-AC-07 | ZTNAのセッション有効期間を短くし、本番アプリは再認証を求めること | Should | P2 |

### 7.3 検知(FR-DT)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-DT-01 | AWSアカウントを用途ごとに分けること(管理、ログ、セキュリティ、本番、検証) | Must | P1 |
| FR-DT-02 | 全アカウントの操作記録(CloudTrail)を、ログ用アカウントに集めること | Must | P1 |
| FR-DT-03 | 脅威検知(GuardDuty)を全アカウントで有効にし、セキュリティ用アカウントで一括管理すること | Must | P1 |
| FR-DT-04 | 設定の記録と評価(Config)を有効にすること。記録するリソースは費用を見て絞ること | Must | P1 |
| FR-DT-05 | 検知結果を1か所(Security Hub)に集め、セキュリティ基準のチェックを行うこと | Must | P1 |
| FR-DT-06 | 組織のルール(SCP)で、ログの停止やリージョン外の利用などを禁止すること | Should | P1 |
| FR-DT-07 | CSPM(RISKEN)で、AWSの設定を継続的に評価できること | Could | P2 |
| FR-DT-08 | 予防的な基本設定(IMDSv2の必須化、アカウント単位のS3ブロックパブリックアクセス、EBSの暗号化)を全アカウントにかけること | Must | P1 |
| FR-DT-09 | SCPで、セキュリティサービスの無効化と、IAMユーザー・アクセスキーの作成を禁止すること(緊急用を除く) | Should | P1 |

### 7.4 自動対応・通知(FR-RS)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-RS-01 | 重大度High以上の検知を、15分以内にチャット(またはメール)へ通知すること | Must | P1 |
| FR-RS-02 | セキュリティグループで全開放(0.0.0.0/0)の危険なポートが作られたら、自動で削除すること | Must | P1 |
| FR-RS-03 | アクセスキーの漏えいが疑われたら、そのキーを自動で無効にすること | Should | P2 |
| FR-RS-04 | 不審な通信をしたEC2を、自動で隔離(通信を止めるセキュリティグループに変更)できること | Could | P2 |
| FR-RS-05 | 自動対応の結果(何を・いつ・なぜ)を記録し、通知に含めること | Must | P1 |
| FR-RS-06 | 自動対応は、誤って動いたときに元に戻す手順を用意すること | Must | P1 |
| FR-RS-07 | ルートユーザーのログイン、ログやセキュリティサービスの停止を、すぐに通知すること | Must | P1 |
| FR-RS-08 | 自動対応から外すための例外(タグなど)と、誤検知を抑えるルールを持つこと | Should | P2 |

### 7.5 ログ集約(FR-LG)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-LG-01 | 次のログを1か所に集め、検索できること:CloudTrail、GuardDuty/Security Hubの検知、ZTNAのアクセスログ、IdPのサインインログ | Must | P2 |
| FR-LG-02 | ログは改ざん・削除できない設定で保管すること(S3のバージョニング、オブジェクトロックなど) | Must | P1 |
| FR-LG-03 | 検索できる期間と保管期間を決めること(→ NFR-LOG) | Must | P2 |
| FR-LG-04 | オンプレ拠点(自宅VM)のログも集められること | Could | P2 |

### 7.6 ダッシュボード・エスカレーション(FR-DB)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-DB-01 | 「リスク」「脅威」「対応状況」の3観点で状況を表示すること(下の表) | Must | P2 |
| FR-DB-02 | アラートごとに、状態(未対応/対応中/完了)と担当者を管理できること | Must | P2 |
| FR-DB-03 | 対応期限(→ NFR-OPS-02)を過ぎたアラートを、代表に自動でエスカレーションすること | Must | P2 |
| FR-DB-04 | 月ごとの推移(件数、対応時間)を見られること | Should | P2 |

ダッシュボードに出す指標(案):
| 観点 | 問い | 指標の例 |
|---|---|---|
| リスク | 弱いところはどこか | Security Hubのセキュリティスコア、Configの非準拠リソース数、MFA未設定の人数、古いアクセスキーの数 |
| 脅威 | 今、何が起きているか | GuardDutyの検知数(重大度別)、ZTNAで拒否したアクセス数、サインイン失敗の回数 |
| 対応状況 | ちゃんと対応できているか | 未対応アラート数、期限切れの件数、検知から対応までの平均時間(MTTA/MTTR)、自動対応の件数 |

### 7.7 ハイブリッド接続(FR-HY)
| ID | 要件 | 優先度 | フェーズ |
|---|---|---|---|
| FR-HY-01 | オンプレ拠点(自宅VM)とAWSを、暗号化した通信路で接続できること | Could | P2 |
| FR-HY-02 | 接続は使うときだけ作り、使わないときは削除できること(費用のため) | Could | P2 |
| FR-HY-03 | オンプレ拠点からAWSへは、必要な宛先とポートだけを許可すること | Could | P2 |

## 8. 非機能要件

### 8.1 セキュリティ(NFR-SEC)
| ID | 要件 |
|---|---|
| NFR-SEC-01 | 秘密情報(キー、パスワード、トークン)をGitHubに上げないこと。コミット前とプッシュ時に自動で検査すること |
| NFR-SEC-02 | GitHub ActionsからAWSへは、アクセスキーではなくOIDCで接続すること |
| NFR-SEC-03 | Terraformの状態ファイルは、暗号化したS3に置き、同時に書き換えられないようにすること |
| NFR-SEC-04 | 保存するデータ(ログ、状態ファイル)は暗号化すること |
| NFR-SEC-05 | Lambdaなど自動対応の権限は、対応に必要な操作だけに絞ること |
| NFR-SEC-06 | GitHub Actionsのアクションはコミットハッシュで固定し、OIDCの信頼条件はリポジトリとブランチで絞ること |

### 8.2 可用性・性能(NFR-AV)
| ID | 要件 |
|---|---|
| NFR-AV-01 | 社内アプリの稼働時間は営業時間(平日9〜18時)を基準とし、冗長化は求めない(小さな会社のため、費用を優先) |
| NFR-AV-02 | 検知と通知の仕組み(GuardDuty、EventBridge、Lambda)は、マネージドサービスで常に動いていること |

### 8.3 運用(NFR-OPS)
| ID | 要件 |
|---|---|
| NFR-OPS-01 | 情報システム担当1人が、週2時間以内で運用できること |
| NFR-OPS-02 | アラートの対応期限を重大度ごとに決めること(下の表) |
| NFR-OPS-03 | 入社・退職・権限変更・アラート対応・自動対応の取り消しの手順書を用意すること |
| NFR-OPS-04 | 月に1回、ダッシュボードを見て振り返る場を設けること |

アラートの対応期限(仮):
| 重大度 | 通知 | 初動の期限 | 期限を過ぎたら |
|---|---|---|---|
| Critical | すぐに | 4時間 | 代表にエスカレーション |
| High | すぐに | 24時間 | 代表にエスカレーション |
| Medium | 1日1回まとめて | 3営業日 | 情報システム担当に再通知 |
| Low | 週1回まとめて | 月次の振り返り | ― |

### 8.4 ログ(NFR-LOG)
| ID | 要件(仮) |
|---|---|
| NFR-LOG-01 | 検索できる期間:直近30日 |
| NFR-LOG-02 | 保管期間:1年(ログが小さく、安いストレージに移すとかえって高くなるため移さない。DOC-03 9.1) |
| NFR-LOG-03 | ログを消したり止めたりする操作は、SCPで禁止し、行われたら通知すること |

### 8.5 費用(NFR-COST)
| ID | 要件 |
|---|---|
| NFR-COST-01 | 常時かかる費用は月3,000円以内を目標とする(仮) |
| NFR-COST-02 | 最初に AWS Budgets(月5,000円で通知)と Cost Anomaly Detection を設定すること |

## 14. 用語
| 用語 | 意味 |
|---|---|
| ゼロトラスト | 場所やネットワークで信頼せず、アクセスのたびに確認する考え方 |
| ZTNA | Zero Trust Network Access。VPNの代わりに、アプリ単位で接続を許可する仕組み |
| IdP | Identity Provider。利用者のIDを管理し、認証を行うサービス |
| SSO | 1回のログインで複数のサービスを使えること |
| MFA | 多要素認証。パスワードに加えて、別の要素で本人を確認すること |
| CSPM | Cloud Security Posture Management。クラウドの設定ミスを継続的に見つける仕組み |
| SCP | Service Control Policy。AWS Organizations で、アカウント全体にかける制限 |
| MTTA / MTTR | 検知から対応を始めるまで/終わるまでの平均時間 |
